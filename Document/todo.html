완료 창 배치를 가상 데스크톱 기준으로 + 축소 끄기 (2026-08-27) 주 모니터 작업 영역만 재서, 모니터가 둘인데도 3840 캔버스를 66% 로 줄이고 있었다. screen_bounds() 가 가상 데스크톱을 쓰고, 05 출력 > 화면에 맞춰 축소 로 끌 수 있다 (현장은 끈다)

완료 멀티 노드 (패널마다 창 따로) (2026-08-27) CF.make_nodes() 가 뷰포트를 노드로 쪼갠다. apply_regions 의 단일 노드 assert 제거, 노드마다 프로세스 기동. 2.4 항목 해소
완료 미리보기 축소 버그 수정 (2026-08-27) res_w 를 줄이는 방식이라 다중 패널에서 안 먹었다 (창 크기가 패널 해상도에서 나온다). scale_regions() 로 뷰포트 사각형을 직접 줄이게 고침
완료 마우스 룩 바인딩 제거 (2026-08-27) Config/DefaultInput.ini 의 Turn/LookUp. 따라가기를 켜면 마우스 델타가 벽 화면을 통째로 돌렸다. WASD/QE 이동만 남김. 방향 전환이 필요하면 키나 게임패드 축에 붙일 것

2.2 벽 이미지 해상도 병목

영상 크기 하드코딩은 해소됨 (2026-08-27). video.Plan 의 out_w=3840 기본값을 없애고 벽 화소 수를 그대로 쓴다. 77 m 벽이면 9872 x 2692 가 나온다. 전에는 벽이 얼마든 3840 이라 2.6배 모자랐다.

대신 07 경고 기준 > 영상 가로 경고 (px) 가 생겼다 (기본 4096). 넘으면 하드웨어 디코더가 못 열 수 있다고 경고한다. 소프트웨어로는 열려서 개발 PC 에서는 멀쩡해 보이는 것이 함정이다.

아직 남은 것: 넘었을 때의 실제 대안. 이미지 시퀀스 출력도, 프로젝터별로 나눠 내는 경로도 아직 없다. 지금은 경고만 하고 사람이 판단한다. 프로젝터 합성 경로(ProjectorPlan)는 중간 벽 이미지를 아예 안 만들어서 이 병목을 비껴간다.

2.3 벽 이미지 해상도

해소됨 (2026-08-27). res_w = 2560 하드코딩을 없앴다. 04 LED 에서 픽셀 피치를 받아 가로 화소 = 전개 길이 / 피치 로 유도한다. 끄고 가로 화소를 직접 넣을 수도 있다. 피치는 이제 꺾인 벽에서도 보인다 (전에는 다중 패널 전용이었다).

screens_and_viewports, build, apply_regions, report.summarize 의 res_w 기본값을 전부 없앴다. 안 넘기면 TypeError 가 나므로 2560 이 조용히 되살아날 수 없다.

2.4 다중 노드 (LED 프로세서 입력 분할)

구현됨 (2026-08-27). 05 출력 > 패널마다 창 따로 (멀티 노드) 를 켜면 뷰포트마다 노드를 하나씩 만들어 창과 프로세스가 따로 뜬다. 창 안에서 뷰포트 좌표는 원점 기준으로 다시 잡히고, 프레임 동기는 ethernet 배리어로 자동 전환된다. 소리는 프라이머리만 낸다.

입력 동기는 해소됐다 (2026-08-31). 노드가 둘 이상이면 inputSyncPolicy 를 ReplicatePrimary 로 쓴다. 프라이머리가 키 상태 맵을 매 프레임 직렬화해 나머지에 복제한다 (DisplayClusterPlayerInput.cpp). 노드마다 창이 따로 뜨면 OS 는 포커스가 있는 창에만 키를 주므로, 안 켜면 그 노드만 움직여 벽이 어긋난다.

같이 고쳐야 했던 것

Config/DefaultInput.ini 의 DefaultPlayerInputClass 가 EnhancedPlayerInput 이라 설정이 통째로 무시되고 있었다. inputSyncPolicy 를 읽는 주체가 UDisplayClusterPlayerInput 인데 그 클래스가 아예 생성되지 않았다. UEnhancedPlayerInput 을 상속하므로 갈아끼워도 기능 손실은 없다.

붙었는지는 로그로 본다: LogDisplayClusterGame: Native input sync policy: ReplicatePrimary. 이 줄이 없으면 클래스가 안 붙은 것이다.

쓸 때 포커스는 node_0 창에 둬야 한다. 복제되는 것은 프라이머리의 입력이다. 그리고 복제되는 것은 입력이지 결과가 아니므로 게임플레이가 노드마다 결정적이어야 한다 (실행 인자의 -fixedseed 가 이 때문이다). UMG/Slate 위젯 입력은 이 경로를 타지 않는다.

남은 것: 여러 PC 로 나누기 (지금은 전부 host 127.0.0.1).

2.4b 곡면 벽의 출력 분할 (프로세서 입력이 여러 개일 때)

BentWall 은 뷰포트를 하나만 만든다 (config.py:35). 벽 전체가 워프 메시 컴포넌트 하나에 묶여 있어서 make_nodes() 가 쪼갤 단위가 없다. 프리셋에 multi_node = True 가 켜져 있어도 곡면에서는 아무 효과가 없다.

LED 프로세서가 패널별로 입력을 따로 받는 현장이면 워프 메시를 N개 컴포넌트로 나눠 구워야 한다. column_us(전개 길이 방향 열)를 N묶음으로 가르는 형태라 크지 않고, 뷰포트가 N개가 되면 make_nodes·apply_regions·창 배치는 기존 코드가 그대로 받는다.

스펙 대기

분할선이 실제 패널 경계와 화소 단위로 일치해야 한다. 임의로 등분하면 이음매에 검은 줄이나 겹침이 생긴다. 패널별 가로 화소 수를 받기 전에는 만들지 않는다 (2026-08-31 결정).

필요 없을 수도 있다. 프로세서가 큰 입력 하나를 받고 그래픽카드가 NVIDIA Mosaic 로 여러 출력을 한 데스크톱으로 묶어 주면 지금 구성 그대로 나간다. 평면 4장을 꺾어 붙인 형상이면 PanelChain 경로라 이미 된다.

2.6 column_us 가 R=0 에서 퇴화 열을 만든다

BentWall(fillet_r=0) 은 이제 죽지 않는다 (0 나눗셈 가드 완료). 하지만 column_us 가 같은 값을 호 분할 수만큼 되풀이해 중복 열 24개를 만들고, 워프 메시에 퇴화 삼각형이 생긴다.

우회로 둘 다 있다: fillet_r = 1.0 (호 1.6 cm, 사실상 직각) 또는 다중 패널로 모델링 (indoor_corner90 이 그 방식). 진짜 직각이면 다중 패널이 맞다.

3현장 값 확인 대기

지금 계산은 전부 예시 값 위에 서 있다. 실제 도면이 오면 다시 돌려야 한다. 필요한 항목은 03-drawing-requirements.md 에 정리돼 있다.

Document/04-site-input.html 을 브라우저로 열면 필요한 외부 입력이 누구에게 받을 것인지로 묶여 있고, 그 자리에서 채우면 플러그인이 그대로 읽는 프리셋 JSON 이 나온다 (2026-08-27 신설). 받은 파일을 Config/AnamorphicRig/ 에 넣으면 끝이다. 폼이 채우지 않은 값은 예시 기본값이 들어가고 _notes.assumed 에 가정값으로 남는다.

항목왜 필요한가
전개 길이, 높이, 꺾임각, 라운드 R지금 값은 협의 기준값이지 도면 확정값이 아니다
볼록 / 오목오목이면 수평 화각이 48° → 146° 로 폭증한다 (확인함). 단일 뷰포트로는 감당이 안 되고 프로젝터 배치도 통째로 달라진다
벽 하단이 지면에서 몇 m 인가 (base_m) 이 한 숫자가 가능한 구도를 통째로 정한다 (2026-09-02 확인). 벽이 눈에서 덮는 앙각이 여기서 나온다. 지금 값 5.0 m 면 +2.9° ~ +34.9° 라 수평선(0°)이 화면에 없다. 즉 지면이 보이는 구도(물체 전체를 바닥과 함께 담는 그림)가 원리적으로 불가능하고, 콘텐츠를 벽 뒤 공중에 뜬 디오라마로 다시 구성해야 한다. 1.0 m 면 -1.0° ~ +30.2° 라 수평선이 들어온다. 비교용 프리셋 probe_site_curved_low 를 만들어 뒀다.
이 값은 "전개 길이, 높이, 꺾임각" 항목에 묻혀 있었는데 그 셋과 무게가 다르다. 따로 물어야 한다
관람 거리와 눈높이눈높이 1.6 m 는 일반값
두 지대의 표고 차벽이 선 지대와 관람 지대가 다르면 반드시 필요
프로젝터 사양해상도, 렌즈 화각 범위, 광량(lm). 대수의 하한을 밝기가 정한다
캘리브레이션 방식카메라 측정(VIOSO 등)인가 CAD 계산인가. 측정 기반이면 곡면이 부담이 아니고 7단계의 성격도 달라진다
패널 장수와 장별 가로 화소 수 출력 분할선이 여기서 나온다 (2.4b). 실제 패널 경계와 화소 단위로 맞아야 이음매에 검은 줄이나 겹침이 안 생긴다. 장별 화소 수는 짝수여야 한다
장별 물리 폭 (전개 길이) 가로 화소 수와 대조한다. 안 맞으면 장마다 픽셀 피치가 다르다는 뜻이고, 벽 전체를 한 피치로 유도하는 지금 계산이 깨진다
프로세서 입력이 큰 것 1개인가 패널별 4개인가 1개면 지금 구성 그대로 나간다. 패널별이면 2.4b(워프 메시 분할)가 필요하다. 이 한 줄이 작업 유무를 가른다
연속 곡면인가, 평면 여러 장을 꺾어 붙인 것인가 평면 조합이면 PanelChain 경로라 이미 된다. 연속 곡면이면 BentWall 이고 분할이 아직 없다
그래픽카드 NVIDIA Mosaic 가능 여부 출력 단자 하나로는 9872 화소를 못 보낸다 (DP 1.4 / HDMI 2.1 한계 약 7680). Mosaic 로 여러 출력을 한 데스크톱으로 묶으면 2.4b 없이 넘어간다

4영상 색 패스스루

우선순위 낮음 프리뷰 정확도 문제다. _curved.mp4 를 LED 프로세서에 직접 넣으면 엔진을 안 거치므로 영상 경로에서는 이 문제가 없다.

영상 1:1 패스스루 를 켜면 자동노출과 ACES 톤커브가 꺼진다. 측정 결과 최대 채널 오차 136 → 71. 0 이어야 할 채널의 누출(탈색)은 거의 잡혔다.

남은 문제: 주 채널이 어두워지는데 채널마다 비율이 다르다 (0.50 ~ 0.94). 노출 문제라면 세 채널이 같은 비율로 줄어야 한다. 3×3 색공간 행렬이 아직 끼어 있다는 뜻.

  • Working Color Space 프로젝트 설정
  • M_MediaPlate_Opaque 가 Lit 인지 Unlit 인지 (Lit 이면 태양광·스카이라이트 색이 곱해진다)
  • r.TonemapperOutputDevice 등 출력 디바이스 변환
  • 포스트프로세스 Color Grading 기본값이 실제로 중립인지

판단: 여기서 멈추고 LED 프로세서에서 캘리브레이션 하는 것이 현장에서 흔한 방식이다.

재측정: 영상 파일 을 TestPattern_wall.mp4 로 두고 빌드 → 실행 → 화면 캡처 → 원본 프레임과 같은 좌표의 컬러바 픽셀 비교. 컬러바 x = 210/640/1065/1490/1920/2350, y = 120.

함정

MediaExample 계열 영상은 평균 휘도 0.0 인 거의 완전 검정이다. 원본부터 그렇다. 눈으로 확인할 때는 반드시 TestPattern 쪽을 쓸 것.
